# omp-ask-more

English | [简体中文](README.zh-CN.md)

- **The `ask` tool**
  - `ask` tool registration — Does: registers a tool named `ask` that replaces the host's own `ask`, whose `execute` parses the questions, resolves the evidence, and hands one compiled HTML form to the host's `ask` through `ctx.invokeTool({ html })`. When: the model calls `ask` in any session where the tool is active. Example: `pi.registerTool(tool)` in `index.ts`, invoked as `invoke<AskToolDetails>({ html: compileForm(questions, evidence, ctx.cwd) }, …)`.
  - Tool flags — Does: declares `loadMode: "essential"`, `approval: "read"`, `strict: true` and `concurrency: "exclusive"`, so the tool is always offered, needs no special approval, the provider constrains arguments to the schema, and only one form is open at a time. When: fixed at tool registration on plugin load. Example: `strict: true`, `concurrency: "exclusive"`, `loadMode: "essential"` in `index.ts`.
  - `askToolRenderer` delegation — Does: delegates result display to the host's own ask renderer, so the transcript card draws every question and answer the way the native tool does. When: when the host renders an `ask` tool result. Example: `renderResult: (result, options, theme) => askToolRenderer.renderResult(result, options, theme)` in `index.ts`.
  - Tool description — Does: carries a model-facing description that states the tool's purpose and lists its documentation topics. When: in the tools section of the prompt whenever `ask` is offered. Example: the description in `src/description.ts` ends with "Topics — read the one a call needs before making it:" followed by `xd://ask/routing`, `xd://ask/rounds` and `xd://ask/results`.
- **Parameter schema and call rejection**
  - `parametersSchema` — Does: defines the wire schema as one root object holding `questions[]` plus sibling `evidence[]` and `demos[]` arrays; each question carries `id`, `question`, `header?`, `brief {where, what, how, diagram?, risks?}`, `options[{label, description?, tradeoff, holds_when?, cost?}]` (2–5) and `recommended?`, with evidence entries attaching by question `id` and `kind` (`file` or `text`) picking their shape, and demos attaching by question `id` plus option `label`. When: in the tool's `parameters` schema whenever the model calls `ask`. Example: `parametersSchema` in `src/schema.ts`; a call is `ask({ questions: [{ id: "retry-strategy", … }], evidence: [{ question: "retry-strategy", kind: "file", path: "src/retry.ts", start: 41, end: 58 }], demos: […] })`.
  - `parseParams`/`validate` — Does: maps the wire shape into internal discriminated unions and rejects problems the schema cannot state — evidence or a demo naming a question `id` or option `label` the call does not hold, a field of the other `kind`, a second demo on the same brief or option, duplicate or empty question ids, a label starting with "Other", a `recommended` index out of range — listing every problem of every question at once before any UI opens. When: on every `ask` call, at the start of `execute`. Example: `parseParams` in `src/schema.ts` produces problems like `demos[0].question: "x" is not the id of any question in this call`.
  - `rejectedResult` — Does: returns a rejection as an error result reading `ask rejected:` followed by one `- <problem>` line each, and separately rejects outright in sessions that cannot prompt the user. When: when `parseParams` finds problems, or when `ctx.invokeTool` is undefined (e.g. print mode). Example: `"ask needs an interactive session, and this session cannot prompt the user"` in `index.ts`, and `rejectedResult` in `src/result.ts`.
- **Model-facing topics**
  - `docTopics` — Does: serves body-only markdown topics through `docTopics()`, which the host mounts as `xd://ask/<topic>`. When: when the model reads `xd://ask` or a topic of it. Example: `docTopics` in `src/description.ts` loads `src/topics/routing.md`, `rounds.md` and `results.md` from disk at call time.
  - `xd://ask/routing` — Does: tells the model every question needing the user's answer — including ones a skill or workflow says to ask in chat — MUST go through `ask`, and maps instruction parts onto `header`, `brief`, `options`/`recommended` and the call itself. When: read before putting a question, choice or confirmation to the user. Example: `src/topics/routing.md` opens "You MUST put every question that needs the user's answer through `ask`".
  - `xd://ask/rounds` — Does: explains the one-form-per-call layout, how to batch independent questions of a round and sequence dependent ones, and that a rejected call lists every problem to fix and retry. When: read before composing a batch or retrying a rejected call. Example: `src/topics/rounds.md`: "Put the independent questions of a round in one call, or one question per call when the instruction asks one at a time".
  - `xd://ask/results` — Does: explains each answer line (`id: label`, `id: "text"`, `id: (no answer)`, `id: (timed out: …)`), `Option notes:` lines, and what an interrupted or cancelled form means. When: read before interpreting answers, cancellations, custom answers or timeouts. Example: `src/topics/results.md`: `` "`id: (timed out: …)`: the form closed at its timeout before the user answered this question; decide it yourself, say what you chose, and continue." ``
- **Skill prompt rule injection**
  - Skill ask rule (`context` hook) — Does: a `context` event hook that, when `ask` is active, appends a rule to the copy of a user-invoked skill message sent to the model, so a skill prescribing chat questions still routes them through `ask`; the persisted message, `/tree` and transcripts keep the original. When: before every model call that has a user-attributed skill prompt (`/skill:<name>`) in the outgoing history. Example: `pi.on("context", …)` in `index.ts` calls `withSkillAskRule`, which appends `` `[IMPORTANT: Any question, confirmation or choice the skill above puts to the user MUST go through the `ask` tool, NEVER into your reply, even where the skill says to ask in chat or shows how the questions look in your reply. Keep their content, order and recommendations.]` `` (`src/skill-prompt.ts`).
- **Form compilation and evidence**
  - `compileForm` — Does: compiles the whole call into one `<form>` with one `<fieldset>` per question — `<legend>` header, Where/What/How paragraphs, evidence, a Mermaid diagram drawn as text art, risks, question demo, the options each with tradeoff and a `(recommended)` mark but no preselected radio, option demos, then the question and its `radio` inputs named by question `id`. When: on every `ask` call that passes validation and the readability gate. Example: `compileForm` in `src/form.ts` wraps `questionHtml`, which emits `<fieldset>`…`<label><input type="radio" name="${id}" value="${label}">`.
  - `resolveEvidence` — Does: reads file evidence itself — `start`-`end` inclusive, `start` alone is one line, neither shows the file's first 40 lines, read up to `end` and no further — with tabs as two spaces and trailing whitespace dropped; quoted text is shown under the source the model names, marked as not verified; a directory or unreadable file shows its reason instead of blocking the ask. When: on every passing `ask` call, before the form opens (`resolveEvidence` runs per question in parallel). Example: `src/brief.ts`; a text entry renders as `<source> · quoted by the model, not read by ask-more` in `src/form.ts`.
- **Readability gate**
  - Readability gate — Does: resolves the host's `judge` role chain (`modelRoles.judge` and its fallbacks, then the session model only when the chain holds no native judgment model) and asks it yes/no questions about every sentence and about every code or abbreviation (issue numbers, `§3`, commit hashes, `VM110`-style terms) found in each question's form section, at most 8 judgments at a time and 30 s overall, billed as `ask-readability`. When: at every `ask` call, before any UI opens and after parameter validation, only when `readability.judge` is on and the session resolves a judge. Example: `sessionJudge`/`resolveJudge` in `index.ts`; sentence questions `actor`/`unshown`/`jargon` in `src/readability.ts`, `JUDGE_DEADLINE_MS = 30_000`.
  - `readabilityProblems` rejection — Does: rejects the whole call when one sentence names no actor, mentions something the dialog never shows only by a name or number, or holds unexplained jargon, or one term is neither common knowledge nor explained — the rejection quotes each failing sentence with its reason and lists each failing term. When: before the form opens. Example: `readabilityProblems` in `src/readability.ts` writes `question "retry-strategy" is hard to understand for a reader who sees only this dialog …`.
  - Retry pass and judge failure — Does: lets the ask through when the call after a rejection is judged (the session's last `ask` tool result, matched also through `xd://ask` device writes, is recognized by the rejection mark), and lets it through with a warning when the judge errors or misses the deadline or the setting is invalid; only the caller's own abort cancels the ask. When: at every `ask` call. Example: `gateUnlessRetry`/`lastAskRejected` in `src/readability.ts`, and the warning `readability check skipped: ${detail}`.
- **Settings**
  - `readability.judge` setting — Does: a boolean plugin setting defaulting to `true`, declared in `package.json` `omp.settings` and read via `getPluginSettings` on every `ask` call; a non-boolean value warns `readability.judge must be true or false` and skips the check. When: read at the start of each `ask` call's readability screen. Example: `package.json` `omp.settings`, `readReadabilityJudge` in `src/settings.ts`; set with `omp plugin config set omp-ask-more readability.judge false` or per-project in `.omp/plugin-overrides.json`.
- **Result rewriting**
  - `answeredResult` — Does: rewrites the host `ask` result's text into `User answers:` plus one line per question in input order — `id: label`, `id: "text"` for a typed answer, `id: (no answer)` or `id: (timed out: the user did not answer; decide it yourself with your best judgment and say what you chose)` — followed by `Option notes:` lines; `details`, notes images and notices pass through unchanged. When: after the host's `ask` returns, on every answered call. Example: `answeredResult` in `src/result.ts`.
- **Language resolution**
  - `tr` language resolution — Does: resolves human-facing text (form labels like Where/What/How, Evidence, Options, warnings) to English or Chinese from `OMOMP_LANG`, then `LC_ALL`/`LC_MESSAGES`/`LANG`, else English, re-read on each generation; model-facing text stays English. When: whenever the plugin produces UI text — form labels at compile time, warning notifications, the registered tool label. Example: `tr("Evidence", "证据")` in `src/form.ts`, `tr` from `omomp-shared/i18n.ts`.
- **Eval script**
  - `eval/readability.ts` — Does: replays recorded asks through `parseParams` and the real readability gate against the judge role chain resolved from local omp settings, scoring rejected questions against `hard`/`readable` labels; the default corpus is `eval/readability-labelled.json`. When: run by hand, `bun eval/readability.ts [corpus.json] [--session-model provider/id] [--out findings.json]` or `bun run eval:readability`. Example: prints `` | rejected questions | `hard` questions not rejected | `readable` questions rejected | ``.
