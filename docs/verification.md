## A skill that asks in chat

Does a model follow a skill that prescribes its questions as chat text, or this plugin's description? Four descriptions were tested in turn: the first, whose only rule for skills was one sentence ("When a skill, workflow or other instruction tells you to ask the user, confirm with them, or let them pick, do it with ask"); the second, rewritten after those runs around the skill's template (`variants/description-rewrite.diff`); the third, which replaced the second with a short general one (commit `e73cd59`); and the current one, which adds to the third what the models' reasoning showed it lacked. Run on 2026-10-30 with omp 18.14.0 in a PTY (the classic renderer's alternate-screen page), with `opencode-go/deepseek-v4.1-flash` and `opencode-go/kimi-k2.7-code`, and for the current description also with `openai-codex/gpt-5.6-luna`, `gpt-6-luna` and `gpt-6.1-terra`. Everything below is in [`skill-priority/`](skill-priority/).

- **Fixture** (`fixture/`): a `PLAN.md` for rate-limiting an orders API with seven open decisions, three source files, and `grilling-SKILL.md`, the `grilling` skill copied from mattpocock/skills `main`. It says "Format a round like so: ❓ **Q1** … ➡️ <your recommended answer>" and "wait for the user's answers before the next round".
- **Launch** (`run.sh`): `--no-extensions --skills=grilling --no-rules --no-context-files`, omp's own 18.14.0 system template and an empty append prompt, so no installed plugin, rule, `SYSTEM_TEMPLATE.md` or `APPEND_SYSTEM.md` takes part. Arms A, R, S and T load this plugin with `-e index.ts --tools=ask,read` (A with the first description, R with the second, S with the third, T with the current one), as do the negative arms N, RN, SN and TN; B has no ask tool (`--tools=read`); C has omp's native ask.
- **Prompt**: `/skill:grilling Grill me on the unresolved decisions in PLAN.md. Do not implement the plan.` omp sends the skill as a user-attributed message headed `[IMPORTANT: User invoked the "grilling" skill; follow its instructions. Full skill below.]`. ### Why the first description lost, and what the later ones changed

The models' reasoning in the A runs names four causes:

1. **It defined ask by "decision".** It opened "Hand the user a decision"; kimi filed a grilling round under something else: "The ask tool is for general decisions, but the skill has its own specific output format" (km-A3).
2. **The skill's template looked more specific.** Its rule for skills said to ask with ask, but nothing about a skill that dictates how questions look in the reply. deepseek weighed "the most specific directive" (ds-V3a); in ds-A1 it first decided to "honor the skill's explicit round format in text".
3. **A call looked expensive.** It asked every option for `holds_when` and `cost`, and evidence, diagrams and demos "whenever". deepseek called a six-question call "enormous" and said it "must be perfect" (ds-V3a), and each deepseek A run had one call rejected before it opened.
4. **Nothing said where the template goes.** kimi expected ask to drop the numbering and recommendation: "The ask function would give a different UI" (km-A3).

The second description opened with what ask does, in the template's own terms ("Shows the user your questions — one, or a whole numbered round, each with your recommended answer — and waits until they answer"), and said this held over any instruction about how questions should look. It mapped a round to one call, question N to the header "QN <title>", the body to the brief, the recommended answer to `recommended`, and "wait for the answers" to the call. It listed as required only what the schema requires, and kept evidence, diagrams and demos for a single substantial decision while adding them in a large round only to the questions whose answer they change. It was replaced because its opening and mapping restate this one skill's template instead of stating a rule for any instruction.

- **deepseek**: in ds-R1 the reasoning settles the conflict in one step: "put questions in ask, with header "QN <title>", body in brief…". Two of three runs still had one call rejected before it opened (ds-R2 `"8,17"`, ds-R3 evidence without `path`), as all three had before; each was resent through ask.
- **kimi**: the reasoning of km-R1 and km-R3 mentions ask 29 and 12 times, km-R1's quoting the opening ("Never write such a question in your reply … So I should use the ask tool"); their tabs are labelled `Q1 - Key` and `Q1 Key`. km-R2's never mentions ask: "The skill says "Format a round like so" with the exact format. I should use that." What remains is kimi not considering the tool at all, the same as in km-A1 and km-A2.

The third description says what the tool does (a dialog that shows the questions with their briefs and waits for the answers, which come back as the result) and when to use it: every question the user must answer, also when a skill or other instruction says how the questions look in the reply. It names no skill and no template. It leaves each field's meaning to the parameter schema and every limit to the rejection that names it.

- **deepseek**: ds-S1 put a five-question first round into ask, with code evidence on its questions; its first call opened, with no rejection.
- **kimi**: km-S1 asked a five-question round in chat. Every "ask" in its reasoning is the verb ("then ask the frontier questions"), never the tool; it drafts the round straight from the template ("the format example shows <question body …> and then ➡️ <your recommended answer>"), as in km-A1–A3 and km-R2.

The current description keeps the third's scope and adds three things the kimi runs named, each in general terms. It says the cursor starts on the `recommended` option, so Enter accepts the recommendation the way "yes" would (km-S1 had weighed how "yes accepts your recommended answer" fits a choice among options). It states the rule in the system prompt's own RFC 2119 words, MUST and NEVER, to stand against the system prompt's "MUST match requested format", and says why: an instruction to ask in chat assumes there is no dialog, so calling `ask` is how to follow it. And it maps the parts of such a question onto `ask`: number or title → `header`, background and analysis → `brief`, choices and the recommendation → `options` with `recommended`, waiting for the answers → the call itself (km-A3 had expected ask to "give a different UI" and drop them). Before the runs, two review agents checked it for single-skill wording and for schema detail repeated from `src/schema.ts`.

- **deepseek**: ds-T1 put a seven-question first round into ask, its first call opening with no rejection. Its reasoning quotes the new text: "the recommended option is cursor position, so it's equivalent".
- **kimi**: km-T1 asked a five-question round in chat. Its reasoning restates the description's answer model in the skill's terms ("The user can say "yes" to accept, or pick another, or write their own") but never mentions the tool; every "ask" in it is the verb. The description now carries everything kimi's reasoning in earlier runs said was missing, and kimi still does not reach for the tool.

### OpenAI models on the `openai-codex` channel

`openai-codex/gpt-5.6-luna`, `gpt-6-luna` and `gpt-6.1-terra` (the channel has no `gpt-6-terra`), one grilling run each with the current description, the same fixture and flags.

- **Before `strict: false`** (the T1 runs, commit `96b4cd5`): all three put the first round into ask, and every call was rejected before it opened. Each filled the optional `demo` with empty values, `{frames: […], path: ""}` or `{frames: [], path: ""}`, which fails "give exactly one of frames or path". Their reasoning then said "Removing all demos" or "Omitting full demo", and the next call carried the same empty `demo`: the models could not leave the field out. The tool sent no `strict` flag, and OpenAI-family backends treat that as strict mode, where every property has to be produced; omp's own provider notes the same (`openai-responses.ts:1907-1918`, #4336). The runs were stopped after 3, 9 and 9 rejections. The summary in l6-TN1 called no ask.
- **After `strict: false`** (the T2 runs): gpt-5.6-luna and gpt-6.1-terra opened a round of 4 and 6 questions on their first call. gpt-6-luna opened a round of 5 on its fourth: first `lines: "7-8,16-17"`, the multi-range form deepseek also tried, then twice a sixth array entry that was reasoning text instead of a question (`"recommended:0}]}]} c? Syntax perhaps JSON invalid? …"`), which omp's parameter check refused. Without strict mode the arguments are no longer grammar-constrained, so a malformed call is possible; each was refused with its reason and resent.

### Changes tried on the first description

Each is a copy of this plugin with one change (`variants/*.diff`), launched by `run.sh` with the A arm's flags, on kimi. Round 1 only, except V3. None was adopted.

- **V1 wording**: the skill sentence also says that a format the instruction prescribes for the reply "describes the questions, not where they go". kimi asked in chat in 2/2, and its recorded reasoning never mentions ask.
- **V2 system line**: the same rule appended to the system prompt through `before_agent_start`. Asked to quote it, kimi recited it from "the Critical section near the end" (`probe-V2`), then asked in chat in 2/2.
- **V3 stop guard**: a `session_stop` handler that, when a turn is about to end on `❓` or `Q<n>` lines or a closing `?`, requests one continuation telling the model to put those questions into ask. kimi moved the round into ask 19 s and 51 s after its chat reply. It corrects only after the round is on screen, the person sees it twice, and every turn that ends on questions costs one more model call; the marker test also misses other formats and fires on rhetorical questions. In ds-V3a the guard never fired.
